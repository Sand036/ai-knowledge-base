
# ADR 002: Embedding Model Selection

- **Status:** Accepted
- **Date:** 2026-10-25
- **Decision:** Use `text-embedding-3-small` with 1536 dimensions.

## Context

The AI Knowledge Base project uses Supabase PostgreSQL with the `pgvector` extension to store document embeddings and perform semantic similarity search.

The database schema currently defines embedding vectors with 1536 dimensions, but the embedding model has not yet been finalized. The model and vector dimensions must be confirmed before creating the Supabase project and applying the database migrations.

The selected model should:

- Produce embeddings suitable for semantic search and Retrieval-Augmented Generation (RAG).
- Be practical for an MVP with limited budget.
- Work with the existing PostgreSQL + pgvector schema.
- Provide a stable and consistent embedding format for documents and user queries.

## Decision

Use the following embedding model:

| Property | Decision |
|---|---|
| Provider | OpenAI |
| Model | `text-embedding-3-small` |
| Vector dimensions | 1536 |
| Database storage | PostgreSQL `vector(1536)` |
| Similarity search | Cosine similarity |
| Usage | Embed document chunks and user queries |

The embedding model must be used consistently for both document ingestion and query embedding.

## Rationale

### 1. Compatibility with the existing schema

The current schema defines embedding vectors with 1536 dimensions. The selected model uses this dimensionality by default, so the schema can remain unchanged.

This avoids unnecessary migration changes before the Supabase project is created.

### 2. Suitable for an MVP

`text-embedding-3-small` is a compact embedding model intended for embedding and semantic retrieval tasks. It provides a practical starting point for the project's MVP without requiring a larger embedding model.

### 3. Consistent semantic retrieval

The same model will be used to embed:

- Text extracted from uploaded PDF and TXT files.
- Document chunks stored in the database.
- User questions submitted to the RAG pipeline.

Using the same model and dimensionality for documents and queries is necessary for meaningful vector similarity comparisons.

### 4. Simple implementation

The model can be integrated through the OpenAI API. The resulting vectors can be stored and queried using Supabase PostgreSQL with pgvector.

The project does not need to host an embedding model locally for the MVP.

## Consequences

### Positive

- Confirms the existing 1536-dimensional schema.
- Keeps the embedding implementation straightforward.
- Supports semantic similarity search using pgvector.
- Provides a practical baseline for later RAG evaluation.

### Trade-offs and limitations

- Embedding generation requires access to the OpenAI API.
- API usage may incur costs as document volume and query volume increase.
- Retrieval quality must be evaluated using the project's own documents and queries.
- Changing the embedding model later requires regenerating embeddings for existing document chunks. Vectors generated by different models must not be mixed in the same similarity-search space.

## Implementation Notes

1. Keep the embedding column defined as `vector(1536)`.
2. Use `text-embedding-3-small` for all embedding generation in the MVP.
3. Store the model identifier in application configuration rather than scattering it across the codebase.
4. Ensure document chunks and user queries use the same model.
5. Evaluate retrieval quality using the RAG evaluation set during weeks 5–7.
6. Revisit the model choice only if evaluation results indicate that retrieval quality is insufficient.
